# Provider capability contract

Status: source-backed readiness model, **not provider acceptance or launch approval**. `inventory/connection-readiness.js` returns independent capability states for each account. Seller Connections displays the full contract. A saved connection or credential probe cannot set an unsupported lifecycle to ready.

| Capability | Current evidence boundary |
|---|---|
| AUTH | Dated provider credential probe and current account connection state. |
| IDENTITY | External account identity recorded by the probe; ownership and complete scope remain separate. |
| CATALOG | Complete provider catalog and exact SKU coverage require independent evidence. |
| LOCATION | Provider location observation does not approve an internal location mapping. |
| LISTING | SKU, listing, pack and mapping coverage require per-listing evidence. |
| ORDER_FEED | Signed delivery or provider reads are partial until missing-event recovery and stock-work intake are proven. |
| RETURN_FEED | Refund/status observations do not establish full RMA and physical receipt. |
| CANCELLATION | Provider cancellation and exact reservation release require end-to-end proof. |
| FULFILLMENT | Provider shipment state does not prove warehouse custody or package handover. |
| INVENTORY_READ | A read task/sample does not establish full account coverage. |
| INVENTORY_WRITE | A publish task does not establish final remote quantity. |
| INVENTORY_READBACK | Independent post-write readback must be bound to mapping, account and location. |
| WEBHOOK | Registration and an accepted signed delivery are separate facts. |
| POLLING | Shopify's current poll records observations; it does not recover missed reservation work. General WooCommerce recovery polling is absent. |
| RECONCILIATION | Target, acknowledgement, independent readback, mismatch case and repair must be proven together. |

The current implementation reports `partial`, `starting`, `setup_required`, `blocked`, `unverified`, or `unsupported` where appropriate. These are operator diagnostics, **not command authorization gates**. Provider-specific mutation paths must continue to enforce tenant, account, SKU, location, physical balance and provider permission checks. A future `verified` claim for any full capability needs dated per-account provider and hosted evidence plus recovery tests; the current source does not supply it.

The Shopify observation poll now rejects an order page with missing stable order ID, provider update revision, line connection, line ID, SKU or positive quantity before writing that order. Each accepted provider revision writes a durable `ci_ingress` receipt in the same transaction as its unified-order observation; same-content replay is safe, changed content under the same revision is a conflict, and a failed page does not advance the scan checkpoint. `npm run test:shopify-order-observation` checks normalization, while `npm run test:shopify-order-observation-isolated` exercises receipt replay, conflict, malformed-page checkpoint and absence of reservation work in a disposable PostgreSQL database with a simulated provider. No real Shopify recovery feed, provider mutation or hosted poll was tested. Shopify's [Order display fulfillment status](https://shopify.dev/docs/api/admin-graphql/latest/enums/orderdisplayfulfillmentstatus) is explicitly a display aggregate, so the poll does not infer warehouse package custody or dispatch from it.

Stock publication now records a durable remote-attempt marker before sending an absolute quantity. A lost response or expired worker lease leaves that outbox task held as `unknown_remote`; later work for the same mapping cannot blindly send another mutation. Shopify, WooCommerce and Amazon MFN have scheduled independent readback of held tasks: a quantity matching the attempted write resolves the task, while a mismatch remains held as `requires_reconciliation`. Amazon's credential probe offers only unique fulfillment-channel codes returned for the verified seller SKU. Publication and readback use the selected mapping code and fail closed when it is missing; no `DEFAULT` channel is invented. Amazon's PATCH path checks the returned `ACCEPTED` status and seller SKU, then independently reads that same channel. This follows the [Amazon Listings Items guide](https://developer-docs.amazon.com/sp-api/lang-en_EN/docs/manage-product-listings-guide) and [PATCH reference](https://developer-docs.amazon.com/sp-api/lang-en_EN/reference/patchlistingsitem), but has not been verified against this account. `npm run test:stock-publication-isolated` passed with simulated Shopify, WooCommerce and Amazon providers accepting writes and dropping responses, matching readbacks, later publications, worker-crash lease recovery, mismatched readbacks, and missing-channel rejection before mutation. `npm run test:amazon-location-discovery` confirms only provider-returned unique channels are offered. `node scripts/verify-worker-console-boundary.mjs` passed with the scheduled jobs. This proves only disposable-database and fixture paths. WooCommerce and Amazon lack full routine drift scans and real provider timing proof. No configured account, real provider, hosted worker, or capacity result is established.

`GET /api/inventory-sync/central/publication-status` now pages tenant-scoped mapping states (attention or all, 100 per page) without returning credentials or provider response bodies. Central Inventory's Channel connections screen displays central target, provider observation, independent readback timestamp/quantity and held task state. The isolated publication fixture verified a held unknown row and its later confirmed readback through the HTTP endpoint. Signed-in browser, hosted alerting and operator reconciliation actions are still unverified.

Publication and reconciliation now share a per-tenant/per-mapping PostgreSQL advisory lock across the provider operation and local recording. The isolated fixture held that lock and verified Shopify readback did not call the provider until release. This covers a local concurrency boundary, not provider eventual consistency after a remote timeout or multi-host acceptance timing.

As of 2026-10-08, `ci_outbox` also retains per-command publication evidence: source ledger event when available, internal and provider SKU/location snapshot, pack size, expected quantity, Agon request fingerprint, sanitized response reference when provided, acknowledgement timestamp, independent readback quantity/time and reconciliation result. Lost responses remain `UNKNOWN_REMOTE_STATE`; received acknowledgement without readback remains `READBACK_PENDING`; a mismatching readback stays held as `MISMATCH`. The owned `_test` fixture now checks all three cases across the supported simulated adapters, including Shopify acknowledgement followed by readback outage. See [Inventory publication acceptance](INVENTORY_PUBLICATION_ACCEPTANCE.md) for the exact test boundary. This adds local implementation/test evidence only; it does not make a configured account ready or enable a provider.
