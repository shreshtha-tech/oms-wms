## Worker ownership and dependency graph

The main worker obtains a tenant-level PG session advisory lock using a checked-out connection. A second main worker for the tenant waits in 15-second intervals. This protects singleton scheduling but does not prove that direct library calls, separate SQS consumers or every auxiliary runner are similarly fenced.

The main inventory loop awaits `runInventoryTaskBatch` (default one task) before progressing. WhatsApp, receipt bridge, seller observation and three readback jobs are scheduled separately with per-job in-process single-flight guards. This separates notification latency from the main inventory loop, but does not create provider/account isolation inside that loop. A publication for provider A can delay order ingestion work and publication for provider B sharing the same tenant outbox.

Publication holds a separate PG connection and a session mapping advisory lock across remote calls. It does not hold a BEGIN transaction across those calls in the reviewed function. The lock prevents overlapping listing writes, but still occupies a bounded-pool slot while waiting for the provider. Worker ownership, readback locks, sender locks and transaction queries share the pool; exhaustion and acquisition waiting must be measured under simultaneous jobs.

Supervisor restart delay caps at 30 seconds and shutdown escalates to SIGKILL after 30 seconds. The worker drains scheduled promises before releasing its singleton lock. This is source evidence; it does not prove that every job completes within the shutdown window, or that recovery satisfies an approved RTO.

## Durable receipt bridge claims (2026-10-08 continuation)

Root cause: the prior Mongo and PostgreSQL bridge loops selected pending rows before processing. Two runner processes could select the same task, perform duplicate local work and race their retry metadata, even though durable consumer receipts prevented duplicate stock. Each store now atomically claims one eligible task at a time with a UUID owner and a two-minute lease. Mongo uses findOneAndUpdate; PostgreSQL uses UPDATE from a FOR UPDATE SKIP LOCKED, tenant-scoped selection. A completion or failure update requires the claim token and processing state. Attempt count increments at claim, including a process crash. An expired lease can be reclaimed under the same durable event identity. Expired processing claims at the eighth attempt become dead in bounded sweeps instead of remaining processing indefinitely. Migration 026 adds PostgreSQL claim_token and lease_until; Mongo claim fields are stored on task documents. Existing held/dead tasks are not automatically replayed.
