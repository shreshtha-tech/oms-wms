## Inbound receipt defect and residual risk

The two inbound handlers both used read-then-write updates on `grn` receipt status. Two confirmations of one draft could each stage a different request ID; one Mongo row could then describe less received stock than the PostgreSQL ledger recorded. Inbound RealTime also omitted the PO release check present in Inbound Create/Edit. The shared unique request ID index, compare-and-set GRN transitions, and release guard reduce those paths. Disposable real MongoDB and PostgreSQL tests now prove the concurrent claim, injected finalization failure, and child-process kill after PostgreSQL commit recover through the original request without a second event. Draft saves and invoice edits now share the same atomic revision claim as receipt staging; a disposable MongoDB race proved only one claimant succeeds. Historical duplicate request IDs, other crash boundaries, and configured-database behavior remain open.

## 1 October follow-up: draft edit and ASN race

A save or invoice edit read a GRN draft, checked that no receipt was pending, then updated MongoDB by ID without a state condition. Receipt confirmation could stage Central Inventory between those steps; the edit could reset the GRN status or lines after staging. Manage ASN also updated the shared `grn` collection by ID, so a request naming an inbound row could overwrite receipt fields. Both inbound handlers now use a monotonically increasing `draft_revision` in their atomic edit/stage transition. Manage ASN requires a pure ASN row and uses the same transition plus its existing `row_version`. A pure ASN row cannot be passed to inbound confirmation as an existing draft. Cancelled inbound drafts cannot be revived through save or confirm.

Expected result for two writers using one draft revision: one update succeeds and the other returns a conflict. `node scripts/verify-inbound-receipt-claim.mjs` passed that race in memory and checked the ASN/cancelled boundaries. `node scripts/run-isolated-inbound-dual-store.mjs` passed the draft revision race against disposable real MongoDB alongside PostgreSQL receipt recovery, then removed both test databases. Complete handler timing, configured Atlas, old GRN shapes, and signed-in browser behavior remain unverified.

## 1 October follow-up: metadata on a committed receipt retry

After PostgreSQL committed a receipt but MongoDB finalization failed, both inbound handlers accepted a retry with the original request ID. Their finalization update spread fields from the retry body over the already staged GRN. A changed invoice or remark could therefore be written as if it had been part of the original receipt. The new disposable dual-store regression reproduced this: `INV-ALTERED` replaced the staged `INV-STAGED` before the fix. Finalization now updates only receipt status, event IDs, and status time; the staged row retains its original metadata.

## 1 October follow-up: offline dispatch evidence guard

Source review found that `/unified/orders/:id/status` could accept an `offline` order and treat the `dispatched` button as proof of physical handover, consuming each reservation and marking lines shipped. No offline order-intake path or pick, pack, and handover evidence contract was found in the current source. The API now returns HTTP 501 for offline staff status changes and leaves seller-platform actions guarded by provider authorization; the Unified Orders screen no longer presents the unsupported buttons. `node scripts/run-isolated-unified-orders.mjs` passed against a disposable PostgreSQL database with an active offline reservation: a dispatch attempt left work status `packed`, preserved on-hand and reserved balances, and created no offline dispatch event. The database was removed. This does not verify a real offline POS order feed, physical workflow, identity/role authorization, or provider dispatch readback.

The worker audit found that the WooCommerce webhook handler stored the provider revision in the order row but dropped it from the queued event. A delayed older task could therefore dispatch after a newer cancellation had already been recorded. The handler now carries WooCommerce's `date_modified_gmt`/`date_modified` into the task. Shopify, WooCommerce, and Amazon worker transitions acquire a PostgreSQL row lock on the provider order and skip an event older than the stored revision where that provider timestamp exists. WooCommerce completion also requires a nonempty exact line set matching the persisted order, rejects completion against a canceled line, and only marks dispatched once every line is shipped.

`node scripts/run-isolated-unified-orders.mjs` passed against a disposable PostgreSQL database that was removed. It exercised signed WooCommerce HTTP ingress and invalid-signature rejection without persistence; stored two ordered revisions and proved the older task made no stock event after a newer cancellation; checked completion arriving before processing and duplicate completion; rejected empty completion; and ran eight concurrent cancel/complete races, requiring line terminal status, dispatch events, active reservations, and on-hand balances to agree. It also retained signed/replayed Shopify ingress, Amazon reservation/dispatch, return replay, seller-action guard, offline-dispatch guard, and oversell checks. The shared Shopify/Amazon row-lock path was not stress-tested in this pass. WooCommerce's published default contract defines `completed` as fulfilled, with physical goods normally marked complete after shipment, and documents HMAC signatures and delivery IDs. Store-specific custom statuses, actual provider accounts and delivery, provider readback, and external carrier handover remain unverified. References: [WooCommerce order statuses](https://woocommerce.com/document/managing-orders/order-statuses/); [WooCommerce webhook contract](https://developer.woocommerce.com/docs/apis/rest-api/v2/webhooks); [Amazon ORDER_CHANGE fields](https://developer-docs.amazon.com/sp-api/docs/notification-type-values).

The Amazon source review found a separate quantity boundary: `ORDER_CHANGE` can be `OrderItemLevel` with one item, and each item can report `QuantityShipped` independently of ordered `Quantity`. The worker previously treated `Shipped` as whole-order dispatch while processing whichever items were present. It now accepts stock transitions only from an `OrderLevel` snapshot, requires that its line identity set match the persisted order, rejects a partial `QuantityShipped`, and confirms every mapped line reached shipped state before setting the order dispatched. A `PartiallyShipped` event records a reconciliation marker without changing quantities; cancellation is blocked while the order still has active reservations, and a later full shipped snapshot can consume the reservation. The isolated suite rejected ItemLevel shipment and a partial shipped quantity without ledger change, retained reservation through partial-shipment cancellation, then consumed it once on the full snapshot. `node scripts/run-isolated-unified-orders.mjs` passed and removed its disposable database. This path is fixture verified only; real notification subscriptions, payload variation, status readback, partial-line reconciliation, and concurrent cross-status Amazon delivery remain unverified. The official schema describes OrderItemLevel versus OrderLevel payload size and QuantityShipped as an item field in the [Amazon ORDER_CHANGE notification contract](https://developer-docs.amazon.com/sp-api/docs/notification-type-values).

## 1 October follow-up: cancellation status follows the inventory outcome

`recordIncomingOrder` previously changed local `work_status` to `cancelled` as soon as a provider cancellation arrived. A worker could then reject the cancellation because of a line-set mismatch, a shipped terminal line, or unresolved Amazon partial shipment while the UI still showed the order as canceled. Intake now records provider status separately and leaves local work status unchanged until the provider worker completes the line transitions. Shopify and WooCommerce cancellation workers require a nonempty line set matching the persisted order snapshot, release each active reservation, verify every line is terminal-canceled, and update `work_status` in the same transaction. Amazon does the same after its partial-shipment guard; conflicts preserve the prior local status. The Unified Orders table now shows provider and work status side by side.

`node scripts/run-isolated-unified-orders.mjs` passed against a disposable PostgreSQL database and removed it. It verified that Shopify cancellation changes local work status only after releasing its reservation, Amazon cancellation after a successful shipment preserves `dispatched` while reporting the provider's later `Canceled` status, and Amazon cancellation after partial shipment leaves local work pending with the reservation intact. The suite also rechecked stale WooCommerce cancellation ordering, terminal-state races, signed ingress, reservation/dispatch replay and oversell rejection. `node scripts/run-isolated-central-inventory.mjs` and `npm run typecheck` passed. The database tests use generated fixtures; provider-specific cancellation semantics, live accounts, role permissions, and manual reconciliation of partial shipments remain unverified.

The same unified-orders suite now simulates the outbox crash window after the order reservation transaction commits but before the worker acknowledges its task. It leaves the task `processing`, expires its lease, and runs the real batch claimant again. The retry completed at attempt 2 with one reservation event and one active reservation. This exercises lease reclaim and idempotent replay in the generated database; it is not a process kill/restart test, does not measure a real two-minute lease timeout, and does not test worker deployment recovery.

## 1 October security follow-up: External Apps credential disclosure

The legacy External Apps GET/search/save responses returned stored configuration values, including password/token-like fields. The Salesforce Marketing Cloud connection test also returned its OAuth bearer token, and the browser copied that token into form state for a later save. The API now masks sensitive key names recursively in list, search, and save responses; `[stored]` values are preserved server-side when editing, and the UI renders them as password inputs. The SFMC test endpoint returns `{connected:true}` without returning the access token, and the UI no longer stores that token in browser state.

`node scripts/verify-external-app-secret-redaction.mjs` passed with generated memory-only records and a stubbed upstream OAuth response. It verified masked list/search/save output, preservation of stored fields when placeholders are resubmitted, AES-256-GCM encryption for new and edited secrets, fail-closed behavior when the key is absent, redirect rejection on the outbound OAuth request, and that the provider bearer token is absent from the API response. The key is `INVENTORY_CREDENTIAL_KEY`, shared with the existing Central Inventory credential encryption utility; it must be backed up and kept stable across deployments. This did not contact Salesforce, configured MongoDB, or a signed-in browser. Existing untouched legacy MongoDB documents can still contain plaintext secrets; a reviewed migration and post-migration readback remain open. Atlas recovery, key custody/configuration, and a real External Apps browser/provider retest remain open.
