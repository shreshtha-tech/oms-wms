# ADR-003: Measurable latency, loss and recovery objectives

Date: 2026-10-05. Status: PROPOSED numbers for owner confirmation (D11). No latency, throughput, RPO or RTO has been measured in Phase A.

## Measurement contract

Use milliseconds for latency, seconds for age/recovery and UTC timestamps. Each eligible sample has a trace/correlation ID, aggregate identity, committed revision/event key, start timestamp, terminal timestamp and outcome. Do not put order IDs, phone numbers, names, tokens, URIs or report rows in metric labels or logs. Detailed trace evidence, if necessary, stays in restricted test artifacts with synthetic IDs only.

`event-to-visible` starts at the source transaction's durable commit (Mongo revision+outbox or PG business state+outbox). It ends when the authoritative API returns the expected revision and the visible active browser screen renders that same revision/totals. Record API and browser endpoints separately; an SSE hint, HTTP 202, submitted provider mutation, cached row or task acknowledgement is not “visible”. For intake, also measure valid raw request/SQS accept start→durable ownership and provider-origin event time→visibility when the approved provider timestamp exists. Report the latter as NOT MEASURABLE when the provider omits that timestamp; never replace it with our receipt time.

Use a local single-node Mongo replica set and fresh isolated PG `_test` databases, fake provider endpoints and fake Meta. Emit synthetic correlated events at a declared rate, wait for a steady warm-up, gather at least 10,000 successful samples per flow for p99, then run declared bursts and fault/restart cases separately. Record nearest-rank p50/p95/p99, sample count, time window, event rate, eligible/excluded/error counts and backlog at start/end. Report pending/timeout outcomes as failures rather than dropping them from percentiles; show age of outstanding events. No error or schema-rejected input belongs in “successful latency”, but rejection and unresolved-effect rates must be reported. Cold-start/replay latency is a separate distribution.

## Proposed flow targets

These are engineering budgets, not claims about existing performance. Owner must approve a realistic workload and provider restrictions; Phase F later establishes supported capacity. Initial Phase B measurement envelope: a bounded steady stream without backlog growth, test-stack resources recorded, and for notification acceptance no more than 0.5 eligible messages/sec/tenant with bursts of at most 20. If that envelope is unrealistic, revise sender capacity/policy/targets before approval. No arbitrary production-volume assumption is hidden here.

## Reliability and recovery targets for approval

| Objective | Proposed number and measurement | Limits / concrete owner |
| --- | --- | --- |
| Acknowledged source-event loss | **0 lost acknowledged events**: every successful ingress receipt, approved command or committed ledger event must resolve to a deduped effect or explicit held/rejected/uncertain state after restart/replay. Measure acknowledged count vs durable resolved/pending/review IDs. | Needs transactional Mongo outbox and PG consumer receipts in ADR-002. Counts alone cannot prove no loss; identities/digests must match. Provider events never received/acknowledged are outside local RPO and need subscription recovery evidence. |
| Local acknowledged-write RPO | **0 acknowledged writes lost for process crash** with durable local test-store settings; verify abort/restart/commit boundaries. | Not a backup or host-loss guarantee. Single-node replica set tests cannot prove production high availability or storage durability under host loss. |
| Infrastructure disaster RPO | Draft **≤5 minutes** of committed business data under full store/host loss, with matched restore/checkpoints across both stores. | Production backup/PITR/offsite capability unknown. User describes a free shared Atlas tier with backups off; this was not independently verified and cannot be assumed to meet RPO. Phase I must verify documentation/owner tier facts and measure restore on `_test` stack. |
| Worker crash RTO | **≤60s** from crash detection to worker running again; **≤180s** to reclaim or explicitly classify pre-crash leased work without duplicates. | `scripts/inventory-worker-supervisor.mjs` restart policy; inventory/WhatsApp leases use 2 minutes. “Process up” and “effects recovered” are separate clocks. | Local DB transient-outage RTO | **≤60s** after Mongo/PG becomes healthy to successful owner-store operations; **≤5min** to settle the declared capped test backlog or record review-required effects. | `api/mongo-connection.js` retry cap ~30s with jitter; `reliability/postgres-connection.js`; worker retry schedules can delay beyond target today. Need monotonic, bounded measurement; retries are not proof. |
| Provider outage recovery | **≤10min** after provider recovers for eligible backlog under the approved capacity envelope; uncertain notification outcomes are review-bound, not automatically retried to claim recovery. | Retry caps currently reach 1 hour. An eventual capped retry is not compatible with 10min without explicit recovery wakeup policy or owner-adjusted target. |
| Disaster RTO | Draft **≤60 minutes** to restore stores, validate ledger/reservations/receipt links and resume safe read/write service; provider publishing held until reconciliation confirms baseline. | Phase I full timed restore drill required. No timing evidence exists in this phase. |

## SLO failure semantics

Backlog, held conflicts, auth/credential failure, degraded store and uncertainty must be visible independently from success latency. A poison event held for review is loss-free preservation, but it fails the flow latency target; do not count it as successful delivery. During store failure accept no unpersisted writes, return the owner-store unavailable error and show last-confirmed stale data explicitly. Health liveness still survives while readiness may fail.

Stock-publish age >60s needs operator-visible unsafe/stale classification and an account-specific selling/publishing response approved in D03/D11; do not invent an automated remote zero-stock call or a provider suspension capability. Alerts >60s queued need diagnosis of backlog/quota/eligibility; accepted without delivery >120s is delivery-stale and never an instruction to resend blindly. Disconnected UI must expose stale state and successful authoritative refresh must be measured before clearing it.

Phase B records propagation latency on the disposable stack, Phase E fault recovery, Phase F capacity, Phase G metrics/alerts, and Phase I RPO/RTO restore evidence. This ADR defines how to measure those outcomes; none of those later phases has begun.
