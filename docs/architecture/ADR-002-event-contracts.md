## Proposed envelope and schemas

`event-catalog.json` lists 58 versioned events, each with aggregate/key, idempotency expression, typed schema, producer, consumer, retry/ordering policy, current native contract and decision. `event-schemas.json` is a JSON Schema 2020-12 design artifact with 36 payload definitions and one discriminated branch per event; it is NOT wired to any runtime validator.

Required common fields: `event_id` UUID, `event_type` ending `.v1`, `schema_version=1`, `tenant_id`, `aggregate={type,key,sequence}`, `idempotency_key`, `occurred_at`, `recorded_at`, `source={store,producer,source_revision}`, `payload_digest`, `correlation_id`, nullable `causation_id`, and event-specific `payload`. Version 1 disallows unknown payload/envelope properties. Producer canonically hashes the business payload; delivery timestamps, retries and diagnostics are not part of business identity. Event ID remains stable across retries. Idempotency expressions in the catalog represent canonical serialized tuples (not ambiguous colon concatenation); persist a hash of the tuple where key length would exceed 512 characters. Aggregate keys use canonical string IDs, a tenant and store/domain identity; legacy integer IDs are normalized to decimal strings. Tenant is always validated against authenticated/configured scope, never merely trusted from event JSON.

Party display names can be personal data: event storage requires restricted access/retention, and payloads are never logged. No token, password, URI, OTP, mobile number, full address, credentials, raw provider body, report row or source XML may enter logs/metric labels. Proposed held-voucher events carry an encrypted evidence reference/digest only; the existing encrypted Tally task is not republished as plaintext. Provider order schemas carry only required identifiers/status/lines and eligibility; financial/customer details stay in restricted owner records until D05 defines an approved snapshot schema. `changed_fields`/digest metadata does not authorize copying an arbitrary object.

At compatibility boundaries, an explicit adapter maps current task shapes to `.v1`; it must validate native identity and version, not relabel old JSON as a valid new event. Unknown major version or unapproved metadata module is held for review without an effect. Keep v1 readers until replay retention ends; incompatible changes produce v2 and a reviewed migration/replay strategy. Deleted masters use monotonic tombstones and cannot resurrect through a stale replay.

## Ordering policies (proposed)

- **O1 — ordered local aggregate effects.** Allocate a durable monotonically increasing sequence under the aggregate lock/version update in the same local transaction that writes state and event. Consumer records `(tenant, consumer, aggregate, last_sequence)` and dedupe receipt atomically with effects. Same event/digest is a no-op; same ID with different digest is a conflict; gaps wait or enter review, never leap into a physical delta. No global ordering is promised. Cross-aggregate multi-line orders lock identities in sorted order as `inventory/workers.js` already attempts; transfers have an explicit transaction/group identity so both legs are one effect. Receipt command and result are different local streams tied by request/digest, not an assumed global sequence shared between stores.
- **O_PROVIDER — provider snapshot ordering.** Receipt sequence preserves local arrival order only. Compare an approved provider revision/UTC timestamp per account/order or mapping. Older snapshots cannot reverse terminal/physical effects. Equal revision with different content is review-required. Missing revision is retained as observational/unverified with `stock_eligible=false`; do not invent order using ingestion time. Partial shipment needs explicit line/package identities and quantities before consume/release. Report order requires approved export timestamp plus digest; stock reports lacking source ordering remain held, not last-write-wins.
- **O_LATEST — latest desired-state publishing/projection.** Process per mapping/identity with a lock; re-read current approved mapping and ledger version. Coalesce stale publish requests into the current target, never roll a channel back to an old balance. Record which balance and mapping revision was actually submitted/observed. Unknown provider outcome stays uncertain until readback; submission is separate from confirmation. Read models may ignore lower source revisions but must process deletes and expose last-confirmed revision/staleness.
- **O_DELIVERY — monotonic notification receipts.** Correlate configured tenant + sender + provider message ID. Advance accepted→sent→delivered→read; retain failed/cancelled/uncertain terminal evidence according to approved transition rules, and never let an older receipt regress delivered/read. Receipt dedupe includes provider message/status. An external receipt cannot select another tenant's row.

The current `ci_outbox.id`, task claim `ORDER BY id`, provider timestamps or UI `at` fields do not implement O1. Even with single-worker advisory ownership, retries can run after later available tasks; durable aggregate sequencing still needs implementation and tests. Poll checkpoints must preserve overlap and a safe provider high-water mark established before the scan; resuming after failure must replay without skipping or duplicating business effects.

Retention/dedupe must outlive allowed provider redelivery and operational replay. Draft: retain event/outbox/consumer receipts for 90 days, configurable per legal/PII rules (D11); do not prune receipts while matching business effects can be replayed. A separate compact business-effect key survives longer if records are archived. Request key reuse with changed content is rejected, never treated as a new command.

## Proposed transaction topology: no cross-store dual write

Mongo originating writers (`api/skus.js`, dedicated masters and inbound APIs) commit their local entity revision and **PROPOSED Mongo `_domain_outbox`** in one replica-set transaction. A dispatcher reads this durable collection; change streams may wake it up only if the actual tier supports the needed features (Phase B documentation/owner-fact gate). Poll/reconciliation always remains the safety net. Change-stream resume token must be stored durably; no `watch()`/resume-token implementation was found in the inspected source. No Atlas capability is presumed from driver code.

For a receipt command, a PostgreSQL consumer first validates the version/tenant/source identity/digest and approved PO/SKU/location quantity contract, then commits **PROPOSED `ci_event_receipt` + ledger changes + existing `ci_outbox` carrying the receipt-result envelope** in one PG transaction. `ci_event_receipt` is a proposed general consumer dedupe table, not the existing source-specific `ci_ingress`. Its logical unique key is `(tenant_id, consumer_name, event_id)` plus digest, aggregate key/sequence and effect reference; sequence checkpoint is transactionally fenced. A duplicate cannot repeat stock; failed validation records a held/rejected result without successful ledger effects.

A Mongo receipt-result consumer commits **PROPOSED `_domain_inbox` + GRN projection/revision** in a Mongo transaction. It cannot generate stock. Projection update uses expected request/digest/revision; changed identity or missing command is a review conflict. Lost acknowledgements replay original envelopes. These proposed collections/tables are named for review only: none was created. The general PG domain-event task router, Mongo dispatcher and projector are not current `runInventoryTaskBatch` features; Phase B must implement and prove them after approval.

PO limits need their own approval/claim version: checking mutable Mongo PO quantity during a PG transaction cannot guarantee a stable cross-store limit. D08 must choose an immutable approved receipt authorization (per-PO/SKU cumulative budget/claim with monotonically owned revisions) carried to the PG consumer. The command schema's `max_receivable_quantity` is an authorization ceiling, not permission to trust arbitrary UI numbers; the consumer verifies issuer/identity/revision and cumulative posted quantities before posting. Changes to a PO after authorization cannot retract already committed receipt facts silently.

For PG-originated effects, business state, downstream envelope and dedupe/checkpoint remain in the PG transaction. Retrying provider sends remains an external side-effect boundary: no distributed transaction or unsupported exactly-once promise is made. State-driven publication can converge through idempotent writes/readback; notification uncertainty requires explicit review. Return/transfer consumers preserve the same request digest and exact approved identities, and legacy projections cannot initiate a second receipt/dispatch.
