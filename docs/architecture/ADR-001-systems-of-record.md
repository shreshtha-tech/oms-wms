# ADR-001: System-of-record ownership

Date: 2026-10-05. Status: PROPOSED — owner review required. Phase: A, design only.

## Evidence boundary

`ownership-matrix.csv` covers 42 domain/entity groups with current authority, proposed authority, actual writer entrypoints, readers/caches, multi-writer/no-owner flags and decision IDs. `storage-inventory.md` enumerates every named Mongo collection and PostgreSQL table found in this static audit; `source-evidence.json` supplies file/line call sites and hashes. This establishes what the source says, not whether a database is populated or a workflow executes correctly. No application module was imported and no database was contacted.

The existing PostgreSQL Central Inventory boundary is `inventory/ledger.js:10`: it records `ci_inventory_event`, updates `ci_inventory_balance`, changes `ci_reservation`, evaluates `ci_stock_alert`, and queues `ci_outbox[publish_stock]` inside the caller's transaction. `inventory/db.js:14` supplies BEGIN/COMMIT/ROLLBACK. The schema is `db/migrations/001_central_inventory.sql:3-14`. `inventory/http.js` rejects arbitrary `/api/inventory-sync/events` with 501. These are source contracts; transaction, concurrency and replay execution are NOT RUN in this phase.

## Proposed ownership rules

1. Physical quantities, reservations, receipts, dispatch deductions, stock-bucket changes and transfer movements remain PostgreSQL ledger-owned. Only validated workflow commands may call `applyInventoryEventInTransaction`; UI, Mongo writes, imported provider quantities and generic APIs cannot directly set a balance. `ci_inventory_balance` is the current-state materialization, not an independent authority. Zero balance is a valid value only when returned by its real store; outage never substitutes zero or memory.
2. Mongo remains the commercial master and procurement-intent store, with dedicated domain services. PostgreSQL holds approved identity projections and provider-operational accounts/mappings. A shared code string is insufficient identity: use an owner-approved tenant + source-entity-ID to central UUID association, preserve UOM/pack size, and fail on duplicates. No new bridge may invent missing mappings. Existing PostgreSQL catalog creation via `inventory/central-api.js` and `inventory/workbook.js` must be reconciled with Mongo SKU ownership before automated projection is enabled (D01).
3. Operational sale orders and provider revisions belong to `ci_unified_order` and `ci_unified_order_line` in `inventory/unified-orders.js`. Mongo `sale_orders` remains historical/read-only unless D06 explicitly chooses a migration. `api/sale-orders.js` mutations return 501. Legacy order enquiries read Mongo and therefore do not automatically display provider intake; a projection or UI source change requires an approved event contract.
4. Picking, packing, shipment, carrier handover, bin/lot/serial placement and STO in-transit custody have incomplete operational contracts. Proposed final owner is the PostgreSQL order/WMS domain, sharing the ledger transaction where physical effects occur. This is an owner decision, not an existing implementation: there are no picklist/shipment/bin domain tables in the 45 inspected central tables. Existing `fulfillment_orders`, `picklists`, `shipments`, `stock_transfers` and `generic_records` cannot be treated as operational state just because rows/status labels exist. Preserve current fail-closed routes until D06 defines their transition/identity contracts.
5. ASN/PO/GRN intent is Mongo-owned; PostgreSQL receipt events are the only proof of stock received. Mongo `central_receipt_status=committed` is a projection that must reconcile with the exact PostgreSQL request/event IDs. Current flow in `api/inbound-create-edit.js:234-262` and `api/inbound-realtime.js:219-248` stages Mongo, commits PostgreSQL through `receiveCentralInboundStock`, then finalizes Mongo after that commit (`inventory/wms-operations.js:172`). This is sequential cross-store writing, not atomicity across stores. D08 proposes durable command/event exchange to replace that dependency without adding stock twice.
6. Provider stock (`ci_channel_stock`, `ci_stock_observation`, `ci_program_stock`) is observed evidence. Publish targets derive only from the approved ledger mapping and physical custody. Marketplace-held/FBA/programme quantities do not reserve or consume warehouse stock. `inventory/order-alert-policy.js` and `inventory/workers.js` distinguish custody and MFN/physical-location paths.
7. Alert state is PostgreSQL-owned. `inventory/order-alert-routing.js` chooses recipients, `inventory/whatsapp.js` owns external sends/receipts, `inventory/alert-admin.js` owns audited operator review. No Mongo banner, notification cache or provider acknowledgement may mutate stock. D07 must unify team/legacy dedupe and distinguish receipt alerts from packing authorization.
8. A projection writer may update only its projection fields, checkpoint and dedupe receipt in one local transaction; it cannot originate commercial changes or stock effects. Diagnostic services (`ci_sync_attempt`, heartbeats, UI refresh) only read business facts and write their own diagnostic state. Authentication/OTP/credentials have separate owners and never travel in domain payloads.

These are logical write permissions. Current route-level access is mostly session authentication plus the central tenant guard in `server.js`/`inventory/http.js`; this ADR does not claim role authorization is implemented. Phase H must prove it.

## Disposable stack prerequisite for later execution

Every subsequent database test must create fresh isolated Mongo and PG databases named with `_test` suffixes, use local loopback endpoints explicitly supplied by the harness, and clean up only those databases/processes. A single-node Mongo replica set is mandatory for transactions/change streams. Never inherit configured connection values or fall back to Atlas. Phase A did not create/start a stack because it is design-only. Local `mongod`, `postgres` and `initdb` executables were found; construction/transaction/change-stream capability is NOT RUN. Docker was not found on PATH, which does not prove the native stack cannot be built.

Existing `scripts/run-isolated-mongo-reliability.mjs` is NOT compliant as-is with the new database-name/isolation rule: it uses `codexqa_reliability` (no `_test`) and spreads `process.env` into the child. Before Phase B uses any harness, audit/replace those inheritance and naming rules; owning a disposable Mongo process alone does not prove the PostgreSQL target is disposable. Do not invoke it unchanged. If the required stack cannot be built in Phase B, stop and ask the owner; no Atlas fallback.
