# Reliability repair and production gate — 2026-10-04

**PRODUCTION READY = NO.** Repository reliability defects were repaired and tested. Configured Atlas remains unreachable during TLS negotiation. Controlled fixture evidence does not establish configured-tenant, deployed-worker, or live-provider readiness.

## 1. Root causes

The old Mongo bootstrap retained a rejected startup promise and cached connection mode; transient failure could poison subsequent requests. Several handlers converted connectivity errors into HTTP 500. UI loading catches could represent failed reads as empty results. Fresh configured Atlas evidence separately shows MongoServerSelectionError with ERR_SSL_TLSV1_ALERT_INTERNAL_ERROR / TLS alert 80 on all three servers. This does not prove an incorrect password or a particular Atlas access-list error.

## 2. Architecture changes

Centralized Mongo connection lifecycle, bounded pool, single-flight reconnection and backoff; separate liveness/readiness; Express 4 async rejection containment; bounded PostgreSQL pool and leased-transaction error normalization. Mongo retains legacy/master ownership; PostgreSQL retains Central Inventory, orders, sessions and durable queues. Shared authentication still depends on PostgreSQL. No data migration or invented stock basis was introduced.

## 3. Database changes

Additive migration 019 introduces hashed login-throttling counters with cleanup index. Applied explicitly to the configured local PostgreSQL database and verified; production migration remains a controlled pre-deployment step. SKU Group edits use atomic revision checks and return conflict for stale writes. SKU creation enforces unique code semantics. Purchase-order numbers have an atomic Mongo unique constraint and cannot change after creation; 20 concurrent repeated creates produce exactly one durable draft and 19 conflicts. Existing duplicate numbers cause creation to fail closed pending reconciliation. Mongo counter allocation preserves existing maximum IDs. No reconnection seeding, business-row reset, or silent memory fallback for configured Mongo failure.

## 4. API changes

Legacy handlers consistently return sanitized DATABASE_UNAVAILABLE HTTP 503 for Mongo transport/pool failures. Auth, origin rejection, validation, unsupported methods, resource-not-found and unmounted routes remain distinct. PostgreSQL API boundaries preserve dependency/timeouts and redact constraint details rather than treating them as raw validation errors. Mongo query deadlines return HTTP 504 without poisoning a healthy connection. Authentication protects operational metrics. Request IDs and deadlines make errors diagnosable without exposing connection strings. No automatic database-write replay.

## 5. Frontend changes

Shared failed-read state replaces misleading empty grids, supports retry, and retains mounted form drafts. SKU Group outage/recovery browser test verifies the unsaved draft survives. Request and authentication timeouts bound waiting; identical concurrent mutations share one in-flight request. ExcelJS loads on spreadsheet actions rather than initial GRN rendering. A large dynamic ExcelJS chunk warning remains visible.

## 6. Security changes

Durable login throttling, mutation origin enforcement, safe exception diagnostics, existing SSRF/DNS protections with bounded provider calls, tenant-scoped queue visibility, signed callback and replay safeguards. Admin-scoped legacy Mongo masters are not represented as independently tenant-isolated. Existing server-side authorization and Central Inventory authority remain intact.

## 7. Reliability changes

Safe read-only provider retry with capped exponential backoff, circuit breaker and no retry of permanent/auth errors or uncertain mutations; bounded quota waits; transaction-safe error handling; coordinated drain and pool shutdown. Liveness stays HTTP 200 while the process drains; readiness becomes unavailable. The Render web blueprint explicitly trusts one proxy hop so secure cookies and client-address throttling follow its HTTPS ingress. Existing durable worker leases, inbox/outbox, idempotency keys, and uncertain WhatsApp send handling remain enforced.
