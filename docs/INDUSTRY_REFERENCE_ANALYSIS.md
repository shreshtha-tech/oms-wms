# Industry reference analysis

Reviewed 2026-10-09 against official repository source, documentation and license pages. The comparison is used to identify transferable engineering patterns. No application was selected as a replacement, and no source code was copied.

## Comparison

| Repository | Architecture and relevant data/workflow patterns | Concurrency, tests and operations | License and fit |
|---|---|---|---|
| [ERPNext](https://github.com/frappe/erpnext) | Broad Frappe ERP in Python. Its stock ledger records item, warehouse, quantity delta, resulting quantity, voucher provenance, valuation and posting order. The official [stock-ledger notes](https://github.com/frappe/erpnext/blob/develop/erpnext/stock/spec/README.md) explain stock-ledger replay/reposting and warehouse/item authority. | The repository includes stock-ledger and stock-entry tests and extensive accounting/stock integrations. The source shows a mature domain model, but it is not directly portable to this Node/PostgreSQL application. Its deployment and database design require separate evaluation. This review did not benchmark it or independently audit its security posture. | GPL-3.0. Use its concepts for ledger provenance, reversal/reposting and physical/financial separation; do not copy implementation without explicit license review. |
| [Saleor](https://github.com/saleor/saleor) | API-first commerce platform in Python/Django. Its [warehouse management](https://github.com/saleor/saleor/blob/main/saleor/warehouse/management.py) models allocations against warehouse stock, accounts for existing reservations, orders stock rows for locking, and uses atomic transactions. It supports warehouse selection strategies and all-or-nothing line allocation when stock is insufficient. | Source includes stock and allocation tests. Stable lock ordering and transaction boundaries are useful concurrency references; operational capacity and full security were not independently measured in this review. | BSD-3-Clause. Good reference for deterministic row-lock ordering, reservation-aware availability and transaction-level rollback. |

## Findings for this project

The strongest common pattern is to make ownership and transaction boundaries explicit: immutable stock movements with source-document identity (ERPNext), stable row-lock ordering and all-line allocation rollback (Saleor), isolated inventory domain operations and compensating workflows (Medusa), and configurable allocation timing at an explicit order state (Vendure).

These patterns align with the existing design direction in docs/architecture/ADR-001-systems-of-record.md, docs/architecture/ADR-002-event-contracts.md and the PostgreSQL inventory ledger. They do not authorize a second stock writer. Any transfer into this codebase must preserve PostgreSQL ledger authority, tenant scope, idempotency and auditable business transitions.

License compatibility is materially different across these projects. ERPNext and Vendure are GPL-family; Saleor uses BSD-3-Clause; Medusa's core uses MIT but has separately identified enterprise material. Review file/package-level licenses and attribution before any code reuse. This report recommends pattern-level learning only.

## Limits

This is a bounded architectural review of official source and documentation, not a source-by-source audit of the four repositories, an independent security assessment, a benchmark, or legal advice. Repository activity and documentation were current as accessed on the date above and can change.
