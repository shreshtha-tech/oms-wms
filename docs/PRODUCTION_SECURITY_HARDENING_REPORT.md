## Confirmed failed invariant: SKU import provenance

Problem: an operation may report business success without executing the business effect. Root cause: `api/sku-imports.js` POST validates a configured attribute set, CSV filename and client-provided `success_records` / `failed_records`, then inserts a `generic_records` SKU import history row whose status is derived from those counts. It does not parse CSV or create/update SKUs in this path.

Fresh reproducer: `node scripts/verify-sku-import-provenance.mjs` (run using Node 24.21.0). The verifier deletes Mongo connection settings before dynamic application imports and uses the explicitly empty in-memory fixture. It creates a synthetic active attribute set, submits only a filename and one claimed success, and compares SKU rows before/after. No server, configured DB or genuine provider is contacted.

Expected: disconnected processor returns 501 and writes no Processed import history. Observed: HTTP 201; one Processed import history row; no SKU changes. Result: **FAIL** with assertion `201 !== 501`. This is a reproduced provenance/integrity defect, not a passing security test. It contradicts NO FALSE SUCCESS. No actual production record was created.

Repair status: NOT IMPLEMENTED in Part 1. Required control: fail closed until an approved processor durably executes the import; derive status from authoritative processing results, never from client counts. Preserve existing historical evidence; do not rewrite old import histories automatically. Keep the new regression's expectation unchanged through repair.
