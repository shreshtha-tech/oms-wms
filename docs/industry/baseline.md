# Current OMS/WMS baseline

Inspection date: 2026-10-09 (Asia/Kolkata). Status: **IN PROGRESS**. Baseline investigation was initially read-only; a later user-authorized Flipkart retrieval implementation is recorded separately in [implementation report](../FLIPKART_ORDER_INTAKE_2026-10-09.md).

## Verified architecture

package.json declares React/TypeScript/Vite, Express, mongodb, pg and AWS SQS packages. server.js mounts authenticated legacy /api routes and private /api/inventory-sync routes. inventory/ledger.js uses PostgreSQL through inventory/db.js; migration 001 declares the central ledger, balances, reservations, mappings, outbox, ingress and cursors. Legacy API modules have a separate Mongo abstraction. This is a two-store application; a Mongo operational record does not establish a Central Inventory stock movement.

api/auth-session.js declares named Central Inventory permissions and configured operators, uses scrypt/timingSafeEqual imports and PostgreSQL sessions. Authentication of /api requests is visible in server.js. Authentication alone does not prove operation-specific authorization, object ownership or warehouse boundaries. Role policy and cross-tenant HTTP evidence require separate verification.

reliability/telemetry.js contains request context, allowlisted structured logging, counters and cumulative latency buckets. The inspected code is process-local. It does not establish a durable telemetry backend, cross-service trace propagation or incident retention policy.

### Database schemas and migration behavior — source cross-check, 2026-10-09

`inventory/db.js` is the Central Inventory PostgreSQL migration entry point. It sets a 120-second statement timeout, takes the session advisory lock `ci-schema-migrations`, and submits the explicit ordered list `001`–`029` from `db/migrations/`. The runner does not consult a migration-version/checksum table. Files `001`–`026` and `029` contain their own `BEGIN`/`COMMIT`; `027` and `028` create partial claim indexes with `CREATE INDEX CONCURRENTLY` outside a transaction. After applying the list, the runner checks that both claim indexes exist and are valid. This is source behavior, not proof that a configured database has this schema.

The first migration establishes tenant-scoped SKU/location/account/mapping identities, balances with nonnegative and commitment-sum checks, immutable inventory events, reservation identity, a publication outbox, ingress deduplication and sync cursors. Migrations `002`–`020` extend this schema with order-line state, stock alerts, catalog source rows, import/observation batches, seller OAuth/sync/location/pairing records, unified orders/lines/timeline/returns, WhatsApp delivery and verification, heartbeat, persistent sessions, sales-program allocations, alert teams/admin actions, login throttles, and domain-event receipts/checkpoints/outbox. Migrations `021`–`029` add alert deduplication/status constraints, provider-authority audit and dispatch review, controlled opening-stock batches/lines, publication uncertainty/readback evidence, receipt claim leases and indexes, and a scoped provider-authority correction. Migration `022` includes a one-time data cutover granting provider-authoritative status to existing WooCommerce/Amazon accounts; `029` narrowly reverses that grant for unrelated platforms when the account revision still matches the migration's own audit entry. Review this behavioral data migration against the intended provider policy before applying it to a populated database.

MongoDB is a separate operational store. `api/mongo.js` can use an explicitly optional seeded in-memory mode when no URI is configured and persistence is not required; that mode is not durable. A failed configured connection is represented as unavailable. PO-number uniqueness is established lazily on the first qualifying Mongo insert, and vendor-code uniqueness is established at the vendor write boundary. `scripts/mongo-ensure-indexes.mjs` is a separate additive index tool that requires the exact selected database and `--yes`; its index creation has not been run in this audit. There is no unified PostgreSQL/Mongo schema migration transaction.

Static migration review is complete for the current 29-file ordered list. Whether a prior schema can be upgraded safely, whether the SQL is compatible with the configured PostgreSQL version, and whether the PostgreSQL/Mongo databases have the expected indexes are runtime questions still open. The isolated migration recovery harness exists but was not run here; it creates and drops a uniquely named test database, so it requires a permitted local PostgreSQL connection.

### API, authentication and storage boundary — source cross-check, 2026-10-09

Current `server.js` has 159 literal legacy `/api/*` mounts, each dispatched through `app.all` and the shared session-auth middleware. The current route map exactly matches the 159 entries in the existing October 7 generated route inventory; all handler imports resolve. Seven mounts are absent from `mongoRoutes`. That registry is used only to add a dataset header observer in the route loop, so membership is not proof that a route persists to MongoDB or that non-members use another store. The seven omitted handlers were read: six are stateless/unavailable workflow stubs, while `testSMSConnection` makes a bounded-time HTTPS token request to the validated Salesforce Marketing Cloud subdomain and does not persist the supplied credentials. Its response JSON has no explicit byte cap in the inspected handler; the downstream native fetch behavior and payload exposure have not been tested.

The request boundary order is material: live/ready health aliases, session lookup, login/logout, and the public `/api/inventory-sync` router are mounted before shared `/api` mutation-origin and session middleware. The public inventory router uses route-specific webhook signatures, OAuth state/browser binding, or paired-agent/WhatsApp tokens. Private inventory routes mount only after shared authentication and apply the configured one-tenant boundary. Metrics, operations and database diagnostics are after session authentication. The legacy route table has shared authentication but source inspection does not establish operation-level role authorization across its handlers. CORS helpers in legacy modules do not supply those controls. These are source facts only; there was no HTTP authorization campaign.

The legacy source inventory and API security matrix were generated on 2026-10-07. Their literal legacy route set still matches current `server.js`; their candidate counts and modern-route map are not regenerated here. Existing untracked generated files were preserved. See the [API security matrix](../API_SECURITY_MATRIX.md) for its historical role/object/storage limits and this continuation's route-order cross-check. ### Worker, queue and schedule boundary — source cross-check, 2026-10-09

The Render blueprint starts `scripts/inventory-worker-supervisor.mjs` as its inventory worker. `scripts/inventory-worker.mjs` holds a PostgreSQL session advisory lock for the configured tenant, verifies required schema objects/indexes through migration 028, refreshes a heartbeat, and runs scheduled observations/reconciliation alongside the task loop. Shopify order observation is scheduled every 60 seconds, Flipkart order observation every 15 minutes, and seller/readback reconciliation every 15 minutes. Jobs are single-flight in process; schedules and next-run times are in memory and reset on restart. The task loop claims one PostgreSQL outbox row by default, with `SKIP LOCKED`, two-minute leases, fenced acknowledgements, jittered retries, and held/dead outcomes for uncertain/exhausted tasks. The supervisor restarts short-lived children with capped exponential delay and terminates a stuck child after 30 seconds. These are source mechanisms; deployed worker count/configuration and task recovery are not runtime-verified here.

Amazon SQS has a separate `inventory:amazon-sqs` command and is not started by `render.yaml`. Its consumer long-polls up to ten messages for 20 seconds, processes each sequentially, calls transactional ingress acceptance, then deletes that message. A per-message catch leaves a rejected message unacknowledged and continues to later messages; the CLI catches poll-level failures and backs off. Ingress uses notification ID plus payload digest and writes local state/outbox in the PostgreSQL transaction before acknowledgement. There is no application-level durable quarantine for failed messages; their redrive/DLQ behavior depends on queue configuration. `ReceiveMessage` does not set or extend visibility, and queue visibility, redrive/DLQ, IAM resource policy, Amazon subscription, hosted SQS process and its credentials are unknown. The SQS consumer itself verifies no Amazon signature. The [worker source snapshot](worker-boundary-snapshot.json) records relevant source/config hashes.

## Business traces inspected

1. Active SKU import route `/app/sku-import` → browser CSV parse → sequential `/api/skus` POST/PUT calls → `/api/sku-imports` request that always returns 501. Individual rows can persist before the final failure, whose message says no SKU changes were made; the active screen only shows that error toast. This is a source-confirmed partial-write and false-outcome-reporting defect, not a runtime-reproduced data-loss claim. Individual SKU validation/indexes do not provide file-level transaction/idempotency. The alternate `RecordedSkuImport` is unreferenced and its generic history writes are also blocked; it is not the active route.
2. Provider order webhook/SQS intake → ingress identity/hash dedupe → transactional order observation/outbox → worker mapping and provider-revision fence → line-specific reservation/cancel/dispatch transitions → ledger SKU/balance locks and immutable event → alert/publication outbox. Shopify/Woo/Amazon cancellation and partial-shipment source paths are now traced; provider semantics and real-store replay/concurrency remain unverified.
3. Flipkart connection verification → listing sample; diagnostic probe → token and one filtered shipment page. A user-supplied execution confirmed HTTP 200 and sampled field names. A subsequent authorized adapter scans backward from a configurable start (1970 by default), paginates/categories, splits searches at 5,000 results, records order observations and checkpoints order and cancellation histories independently. The endpoint excludes Flipkart Advantage and makes no promise of retention back to 1970. Recurring refresh scans seven recent days on both `orderDate` and `cancellationDate`; generic later non-cancellation status changes are not shown to have a supported delta filter. Multi-window fixture, full configured backfill, owned-PG restart, seller reconciliation and late-change provider behavior remain NOT RUN.
4. Receipt envelope → exact schema/digest/tenant checks → consumer advisory lock, duplicate receipt and aggregate-sequence checks. Full Mongo staging → PG effect → Mongo projection needs transaction and restart tests; source shape alone is insufficient.
5. Central Inventory page → same-origin authenticated `/api/inventory-sync` routes → configured tenant boundary → PostgreSQL ledger/import batch. Manual stock changes persist a stable request ID in browser storage before POST and reuse it for an uncertain retry; the server derives event identity from that ID and rejects conflicting replays. Workbook count intake inspects/ previews the file without changing stock, requires exact existing SKU/location/balance identity, snapshots balance versions, and commits all rows as `physical_count` ledger events in one transaction. Stale previews fail rather than overwrite concurrent stock changes. Catalog imports do not change stock. These are source-traced controls; route/PG integration and concurrent commit outcomes remain unverified here.

## Five finding classes

Verified facts are the named source behavior above. A source-confirmed SKU import outcome-integrity defect allows per-row writes before a guaranteed 501 and then reports no SKU changes; database persistence/failure outcomes remain un-reproduced. Incomplete read authorization policy and configured provider behavior remain investigation items rather than confirmed defects. Missing evidence includes provider permissions, runtime DB contention, complete security coverage and hosted recovery. Confirmed capability/configuration gaps include incomplete coverage for some provider adapters, absent npm Dependabot configuration, and other documented boundaries. Flipkart order observation code now exists, but provider-wide completeness and deployment are not proven. These are not evidence of provider failure or an exploitable vulnerability. Business decisions include permitted stock exceptions, role/read policy, warehouse scope, import atomicity and D11 workload/latency/recovery targets.
