### Migration and index source audit — 2026-10-09

The current PostgreSQL runner's explicit list is contiguous from `001` through `029`. Migrations `001`–`026` and `029` wrap their work in per-file transactions; `027` and `028` intentionally use `CREATE INDEX CONCURRENTLY` outside a transaction. The runner serializes the full sequence with a session advisory lock and validates those two indexes after the sequence. There is no persisted applied-version/checksum ledger, so repeatability relies on SQL-level idempotence and is not equivalent to detecting edited historical migrations. PostgreSQL documents that concurrent index creation cannot run inside a transaction block and that a failed build can leave an invalid index requiring an explicit drop/retry or concurrent reindex; the local guard detects invalidity but the runner does not repair it ([CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html)).

The guarded `scripts/run-isolated-migrations.mjs` and `scripts/verify-migration-recovery.mjs` are designed to test concurrent first startup, repeated application, data/constraint preservation, an injected transactional failure, pool recovery and lock waiting in a uniquely named local test database. They were inspected but NOT RUN in this audit. Therefore all those outcomes remain unverified for the current checkout. Do not apply the runner to a configured or production database as a substitute for this evidence.

MongoDB schema enforcement is mixed: the explicit `mongo:ensure-indexes` tool is selected-database/`--yes` guarded and additive, while purchase-order and vendor uniqueness indexes are created lazily by write paths. MongoDB documents that a unique index enforces uniqueness and that a build fails when existing values violate the constraint ([unique indexes](https://www.mongodb.com/docs/manual/core/index-unique/create/)). No Mongo index inventory or configured Mongo connection was inspected in this turn. The MongoDB operational store and PostgreSQL Central Inventory are not covered by a common migration transaction or recovery procedure. Before rollout, capture current database/version/index state, rehearse every SQL migration from a prior-schema fixture, test concurrent index failure/repair, and separately verify Mongo indexes and backup/restore on authorized isolated stores. Effort medium; benefit safer upgrade and duplicate prevention; compatibility preserves both stores; risk medium because migrations contain schema and one-time data changes; acceptance: current and previous schema upgrades, repeat-run behavior, failure recovery and post-upgrade invariants pass on disposable owned databases. Validation is NOT RUN.
