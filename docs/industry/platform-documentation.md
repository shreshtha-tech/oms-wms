## Amazon SP-API order and notification contract

[Orders API](https://developer-docs.amazon.com/sp-api/docs/orders-api) currently lists v2026-01-01 for sellers and marks v0 deprecated; its sandbox is static. The [migration guide](https://developer-docs.amazon.com/sp-api/docs/orders-api-migration-guide) documents breaking changes including `NextToken` to `paginationToken`, 24-hour pagination-token expiry, status/channel mappings, and the removal of RDT generation for v2026-01-01 PII access in favor of assigned roles. It states orders older than two years are unavailable, with exceptions for Singapore, Japan, and Australia. Local Amazon order intake does not call Orders API, so these contracts describe a possible reconciliation path, not current local polling behavior.

[LWA connection docs](https://developer-docs.amazon.com/sp-api/docs/connecting-to-the-selling-partner-api) say access tokens expire after one hour and require registered/authorized applications and request identity headers. Local AmazonConnector refreshes and caches LWA tokens and sends `x-amz-access-token` and User-Agent. This does not establish seller role grants or live account access. [Usage plans](https://developer-docs.amazon.com/sp-api/docs/usage-plans-and-rate-limits) are operation/account/application dependent; `x-amzn-RateLimit-Limit` may be absent and does not include every applicable plan. The worker passes a per-account quota callback to the connector, while the connector's instance-local patch limiter is not a shared account-wide budget. No live API request was performed.

The official [`ORDER_CHANGE` contract](https://developer-docs.amazon.com/sp-api/docs/notification-type-values) uses the SQS workflow. OrderLevel notifications contain all order items; OrderItemLevel notifications contain one item. Local `sqs-worker.js` accepts raw or SNS-wrapped messages and deletes them only after transactional ingress acceptance. `ingress.js` deduplicates `NotificationMetadata.NotificationId` plus payload hash and records an outbox item. The local adapter handles `ORDER_CHANGE` and `LISTINGS_ITEM_MFN_QUANTITY_CHANGE`; `workers.js` requires OrderLevel snapshots for stock transitions, holds partial shipment for reconciliation, and rejects unsafe item/package ambiguity. The same official notification schema includes `DestinationPostalCode`; local persistence and retention/privacy obligations for notification payloads need a field-level audit.

The SQS worker does not verify an Amazon signature itself. Its trust boundary depends on the deployed queue resource policy, sender identity, subscription and AWS credentials; those are not verified here. The Render blueprint does not start the separate SQS CLI or define its queue URL/account settings. Readiness does not prove subscription registration or queue health, and its account setup state remains unsupported pending that lifecycle. The local code therefore demonstrates a source-level event consumer, not complete seller synchronization or historical retrieval. [Sandbox documentation](https://developer-docs.amazon.com/sp-api/docs/selling-partner-api-sandbox) distinguishes static mocked responses from dynamic sandbox behavior; Orders API is listed as static. No configured seller, queue or provider request was made.

## WooCommerce REST and signed-order delivery details

The current [WooCommerce REST API documentation](https://developer.woocommerce.com/docs/apis/rest-api/) identifies `wc/v3` as the WP REST API integration; the older `/wc-api/v3` documentation describes the legacy API and should not be used to infer the current adapter contract. [Authentication docs](https://developer.woocommerce.com/docs/apis/rest-api/authentication) state REST keys are attached to a WordPress user and requests follow that user's roles/capabilities; Basic authentication is supported over HTTPS. The local connection validator requires an HTTPS origin and `wooRequest` uses Basic auth for `/wp-json/wc/v3`.

WordPress [REST pagination](https://developer.wordpress.org/rest-api/using-the-rest-api/pagination/) defines `page`, `per_page` (1–100), and `X-WP-Total` / `X-WP-TotalPages` headers for collection endpoints. This provides the generic pagination contract, but the current Woo adapter does not poll order collections; it accepts pushed signed order webhooks. The platform's current [webhook documentation](https://developer.woocommerce.com/docs/best-practices/urls-and-routing/webhooks) specifies a secret-derived delivery hash, an activation ping, and default disabling after five unsuccessful deliveries, configurable by the merchant. The retry/disable threshold therefore varies with store configuration. WooCommerce's optional Store API rate limiting is a distinct API surface and must not be presented as a REST API quota; no general WC REST quota was established in the reviewed docs.

Local evidence is stronger than source inspection alone: `scripts/verify-order-webhook-evidence.mjs` over an isolated disposable PG database exercised actual HTTP signed Woo order delivery, exact duplicate acceptance, same delivery ID with changed content (409), foreign-account/tenant denial, missing tenant failure, and safe DB-unavailable/timeout responses. `inventory/http.js` binds signature checking to raw request bytes, persists delivery ID and payload digest in the transaction, records accepted order evidence, then returns 202. This does not prove a live merchant has registered the endpoint, that Woo retries are configured as expected, or that missed/disabled webhook events are reconciled. Acceptance for a complete operational contract remains: documented configured failure threshold, visible disabled-subscription state, and a tested read/reconciliation recovery path. Effort medium; risk medium because missed events can make order state stale; validate by isolated disable/replay scenarios and a separately authorized read-only merchant reconciliation. No external write was made.

## Database and deployment contracts — 2026-10-09

[PostgreSQL 18 isolation documentation](https://www.postgresql.org/docs/18/transaction-iso.html) identifies Read Committed as default and explains statement snapshots and waiting/rechecking locked rows. Local reliability/postgres-transaction.js sends BEGIN without overriding isolation; deployed defaults/version are unknown. Ledger locks and unique identities are therefore material mechanisms, not an automatic consequence of using transactions. Serializable/repeatable-read failures require whole-transaction retry; no blanket isolation change is proposed. Connectivity loss during COMMIT remains an uncertain outcome requiring identity-based reconciliation.

[MongoDB transactions](https://www.mongodb.com/docs/manual/core/transactions/) describes multi-document atomicity on replica sets/sharded clusters and the dependence of majority/snapshot guarantees on commit write concern. Local api/mongo-session.js delegates to driver withTransaction, sets transaction/commit deadlines, and maps UnknownTransactionCommitResult to DATABASE_COMMIT_UNCERTAIN. The helper does not itself set read/write concern; effective caller/client/deployment settings and topology need separate inspection. No configured topology, majority durability or restore proof is claimed.

The current [PostgreSQL CREATE INDEX contract](https://www.postgresql.org/docs/current/sql-createindex.html) says `CREATE INDEX CONCURRENTLY` cannot run inside a transaction and a failed build can leave an invalid index; local migrations 027–028 deliberately use that mode and the runner checks validity afterward. MongoDB's [unique-index contract](https://www.mongodb.com/docs/manual/core/index-unique/create/) says existing duplicate values prevent a unique index from being established. These contracts support the source-level migration findings in [reliability and observability](reliability-and-observability.md); they do not establish the configured server versions or current database state.

[Render health checks](https://render.com/docs/health-checks) admits new web instances based on the configured HTTP path and subsequently uses that path to manage running-instance failures. Consequently this YAML does not make dependency readiness a deployment-admission gate. This is a configuration observation; actual hosted dashboard overrides are unknown. Liveness avoids dependency-outage restart coupling, so choosing a readiness health path needs deliberate failure-policy review.

Attached persistent disks are unavailable there, and disk attachment changes zero-downtime behavior. Local web preDeployCommand runs inventory:migrate. Proposed bounded readiness/migration investigation: capture deployed path/version/topology without secrets, compare staged dependency-failure routing and restart behavior, and rehearse additive migration plus previous-app compatibility on owned stores.
