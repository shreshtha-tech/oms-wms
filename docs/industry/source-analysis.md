## Fresh commerce and cancellation review

Saleor [lock_objects.py](https://raw.githubusercontent.com/saleor/saleor/main/saleor/warehouse/lock_objects.py), inspected on main, orders stock locks by primary key and allocation-with-stock locks by stock primary key. Its [reservation tests](https://raw.githubusercontent.com/saleor/saleor/main/saleor/warehouse/tests/test_stock_reservations_management.py) assert multi-warehouse splits, unchanged physical stock, insufficient-stock rejection, allocation/reservation subtraction, replacement behavior and shipping-zone policy. These are test-source assertions, not executed concurrency proof.

Medusa [reserve-inventory.ts at v2.21.2](https://raw.githubusercontent.com/medusajs/medusa/v2.21.2/packages/core/core-flows/src/cart/steps/reserve-inventory.ts) multiplies required quantity, locks deduplicated inventory-item keys, creates reservations and records reservation IDs for compensation. Compensation locks those items again and deletes the recorded reservations. The step chooses location_ids[0]; this is not a template for splitting across warehouses. The locking service implementation and compensation crash durability are outside this inspected file.

Fresh local inventory/workers.js inspection: Shopify prepares uniquely mapped physical lines, sorts by master SKU/location/line, verifies equality with persisted provider line identities, processes all lines inside transaction(), checks terminal state, and validates the active reservation against current mapping before cancellation release. It records canceled terminal lines to reject late recreation. WooCommerce also sorts prepared mapped lines and gates completion on provider dispatch authority. This corrects the earlier incomplete assessment: local deterministic ordering and cancellation identity checks already exist. Their current runtime behavior remains NOT RUN.

inventory/unified-orders.js separates order observation from worker stock effects, ignores stale timestamped updates, refuses to overwrite changed stock-bound SKU/quantity and records review events. Timestamp-free updates remain accepted by its SQL predicate; inspect provider contracts before classifying this as a defect. Do not equate observed/cancelled timeline entries with committed stock effects.

Recommendation: verify existing mechanisms before changing stock logic. Medium effort, low application regression risk for test-only work, high environment dependency. Acceptance: concurrent multi-line orders cannot oversell/deadlock; mapping changes cannot release another SKU/location; late create after cancel remains terminal; lost acknowledgements and changed replays produce no duplicate effects. Validation requires an owned PG stack and actual worker/ledger transactions, not upstream test names or injected queries.

## Queue, ERP and WMS continuation

Local inventory/workers.js claims a tenant-scoped bounded batch through FOR UPDATE SKIP LOCKED, increments attempts, sets a two-minute lease and checks attempts/status when acknowledging or recording failure. Recovery exhausts attempts at eight without granting extra execution. Stock-publication errors after possible dispatch move to held/UNKNOWN_REMOTE_STATE or READBACK_PENDING; they do not blindly retry the remote mutation. Retry delay is capped exponential with jitter. This establishes code mechanisms, not live fencing, fairness, contention or remote outcome correctness.

inventory/sqs-worker.js accepts each notification before DeleteMessage; malformed/rejected messages remain for redelivery while later entries continue. inventory/ingress.js puts message identity/hash, order projection and outbox insert in the same caller-owned PG transaction, rejects changed message replay and returns duplicate for identical replay. Queue sender policy is an external prerequisite, not signature verification performed in this loop.

[pg-boss plans.ts](https://raw.githubusercontent.com/timgit/pg-boss/master/src/plans.ts), master, contains queue/job locking, retry scheduling and dead-letter insertion. [retryTest.ts](https://raw.githubusercontent.com/timgit/pg-boss/master/test/retryTest.ts) checks expiration/failure retry, fixed delay, exponential backoff, a nonzero-delay regression when retryDelay is omitted, capped backoff and manual-retry retention cleanup. These tests were read, not run. The existing local queue already implements the principal retry/claim concepts; adding a second queue is not justified by these sources. Adapt applicable failure cases and measure starvation/recovery first.

[ERPNext stock_ledger.py](https://raw.githubusercontent.com/frappe/erpnext/develop/erpnext/stock/stock_ledger.py), develop, sorts item/warehouse processing gates, validates cancellation/reposting state and supports explicit negative-stock policy. It bounds full-row repost loading to batches and keeps identity/sort fields in its queue. These accounting/backdating assumptions differ from the local immutable event ledger. Use provenance/rebuild test concepts; do not enable negative stock or mutate historical local ledger events.

## Provider cancellation and partial-fulfillment source trace

`inventory/ingress.js` stores Shopify and Amazon delivery identity plus payload hash transactionally before appending worker work; an exact delivery replay is acknowledged without a second outbox effect, while reuse of an ID with a changed body conflicts. `inventory/workers.js` then applies a provider revision fence before processing order snapshots. Shopify validates a stable, exact line set against the persisted observation, sorts prepared SKU/location/line identities, releases only an active reservation with its current mapping, and writes a per-line canceled terminal state; an already canceled line is replay-safe, while a shipped terminal line conflicts. WooCommerce similarly validates mapped line set and quantity, rejects current mapping drift for active reservations, treats `refunded` as financial rather than physical receipt evidence, and marks cancellation terminal only after its per-line transition. Amazon requires an OrderLevel full snapshot for inventory transitions, holds partial-shipment reconciliation, and refuses shipped lines without an active matching reservation; cancellation releases only that active line reservation and records terminal state.

`inventory/ledger.js` adds a second guard: a release must match exactly one active reservation with equal quantity; the resulting reserved-stock delta must remain nonnegative, and the event key is bound to a canonical payload digest. These controls support the stated reservation/cancellation invariant for the traced paths. They do not establish all marketplace payload ordering/quantity semantics, partial cancellations, commit-loss recovery, cross-path completeness, or actual rollback under a PostgreSQL failure. The source trace is not a database test; run the full provider replay/cancel matrix on a fresh owned `*_test` database before closing invariant 4.

## SKU CreateUpdate import workflow trace

`src/App.tsx` mounts `src/eretail/masters/SkuImport.tsx` at `/app/sku-import`. The active screen parses the selected CSV in the browser, caps it at 500 rows and checks that `sku_code` and `name` headers exist. It loads all current `/api/skus`, then sequentially calls `/api/skus` POST or PUT for each valid, nonduplicate row. Per-row API failures are caught and counted, and the UI proceeds to `/api/sku-imports` only after the loop. That route validates CreateUpdate, active Attribute Set and filename, but never receives file bytes or counts as authoritative input; every otherwise-valid import request reaches the hard-coded 501 `SKU_IMPORT_PROCESSOR_UNAVAILABLE`. `apiSend` throws on non-2xx and prefers the returned message; the screen catches it and shows an error toast. Thus the active workflow can already have created/updated some SKU records when it reports that processing is unavailable. The 501 text says “No SKU changes ... were created,” which is false for the end-to-end UI operation whenever one or more earlier `/api/skus` requests committed. This is a source-confirmed user-facing outcome-integrity defect and partial-write path; no database failure injection or configured runtime reproduction was performed.

Each `/api/skus` request is its own persistence operation. POST checks existing codes before insert and also creates/uses a case-insensitive unique Mongo index; PUT validates and updates one existing ID. These controls protect individual SKU identity but do not make the CSV a transaction or idempotent import job. A timeout/lost response can leave the browser unsure whether one row committed; then remaining requests continue and the final processor request still returns 501. The screen also supplies client-derived success/failure counts to that endpoint, but the endpoint does not persist a history row. The entire file is read into browser memory before the 500-row limit is checked, and the initial `/api/skus` GET returns the full SKU collection; byte-size, catalog-size, browser-memory and latency behavior have not been measured. The suggested repair is not to trust those counts: use one server-owned import identity and payload, enforce byte/row limits, validate/preview server-side, then atomically commit SKU changes and authoritative outcome/history under an owner-approved all-or-nothing or partial-success contract.

`src/eretail/masters/RecordedSkuWorkflows.tsx` contains a second exported `RecordedSkuImport` with naive comma splitting and the same per-row mutation shape, followed by `/api/generic` history creation. It is not imported by `App.tsx` or referenced elsewhere in `src` during this search; it is not the active route, but must not be wired in as a workaround because `api/generic.js` explicitly returns 501 for SKU-import writes. Preserve this distinction in future UI work. The route, UI, API helper and supporting registry hashes are captured in [SKU import source snapshot](sku-import-snapshot.json).
