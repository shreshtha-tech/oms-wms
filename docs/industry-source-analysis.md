# Industry source analysis against OMS/WMS

Review date: 2026-10-09. This is a bounded review of selected code paths and test sources, not a complete audit of each upstream system. Source references point to moving branches. Upstream test suites were inspected but not executed here.

## Local system inspected

The inspected top-level tree includes `src/` React/TypeScript screens and Vite config, `server.js`/`api/` Express endpoints, `inventory/` domain services, `db/migrations/` PostgreSQL schema, and Node `.mjs` verifier scripts. Runtime package versions include React 19.2, Vite 7.3, Express 4.22, MongoDB driver 6.21, PostgreSQL driver 8.23, and AWS SQS SDK. `render.yaml` defines deployment services. Existing dated audits, rather than this source sample, hold broader route/security inventories. The project has two distinct persistence domains. Legacy OMS/WMS API modules under `api/` use the Mongo abstraction in `api/mongo.js`. React/TypeScript screens under `src/` include broad eRetail master, inbound, order and WMS modules. Central Inventory runs through `inventory/` and PostgreSQL migrations under `db/migrations/`; `inventory/ledger.js` appends inventory events, checks replay payload hashes and reservation state, locks the SKU and balance rows, enforces nonnegative and reserved-versus-on-hand invariants, updates a balance projection, evaluates alerts and queues publication work in the transaction. `inventory/receipt-bridge.js` stages the source receipt and an outbox entry in Mongo, consumes it with PostgreSQL idempotency and ledger posting, then projects the result into Mongo. This is a durable cross-store workflow, not a distributed atomic transaction.

The README documents Shopify order observation as read-only. The existence of connector modules or settings is not proof that production accounts, provider writes, hosted services or marketplace reconciliation have been verified. `docs/architecture/ADR-001-systems-of-record.md` and `docs/architecture/PHASE_B_EVIDENCE_2026-10-07.md` define intended ownership and evidence boundaries; their stated historical fixture checks are not rerun by this research.

| Reservation and allocation concurrency | PostgreSQL reservation state is coupled to quantity delta and balance update in ledger transaction. | Allocation at a business transition | Local central inventory has unified orders/reservations but ADR-001 marks full pick/pack/handover and some line-state transitions as incomplete or owner-gated. | Receiving and warehouse processes | `inventory/receipt-bridge.js` is implemented for a defined receipt contract. Do not port the large Groovy service or treat similar legacy UI records as authoritative physical state. |
| SKU import | `api/sku-imports.js` currently returns 501 for a valid CreateUpdate request because server-side ingestion is unavailable; the current uncommitted source change prevents the endpoint from fabricating a processed history row. The current UI `src/eretail/masters/SkuImport.tsx` sends individual `/api/skus` POST/PUT requests before posting the import history request; it receives the 501 after those earlier row writes. `scripts/verify-sku-import-provenance.mjs` is documented as an explicit-memory, no-write boundary test. | Medusa’s workflow step model illustrates compensation; Saleor stock tests illustrate atomic failure expectations. None is a ready-made product-import implementation for this Mongo route. | This creates the clearest specific workflow gap: partial SKU writes can precede a failed history record. Design a validated server-owned import contract that does not mutate rows before full validation and records job/results consistently. Decide all-or-nothing versus explicit per-row partial success with product owners. Never alter the separate PostgreSQL stock ledger as a side effect of master import. |
| Queue topology | Local central inventory uses a PostgreSQL outbox plus AWS SQS for queue-backed tasks, as visible in package dependencies, migrations and workers. | [pg-boss](https://github.com/timgit/pg-boss) is a Postgres-backed Node queue; [`plans.ts`](https://github.com/timgit/pg-boss/blob/master/src/plans.ts) and its [test tree](https://github.com/timgit/pg-boss/tree/master/test) are potential comparison points. | Additional queue introduces a second job runtime and operational semantics. Do not adopt without measurements showing current outbox/SQS is insufficient and a migration/ownership plan. |

## Additional maintained stack-specific reference

The initially suggested [`Shopify/shopify-api-js`](https://github.com/Shopify/shopify-api-js) is archived (GitHub marks it read-only and identifies the move). Its webhook guide remains a historical source, but the current package monorepo is [`Shopify/shopify-app-js`](https://github.com/Shopify/shopify-app-js), which lists framework-agnostic `@shopify/shopify-api` and an Express adapter. The current package directory is [`packages/apps/shopify-api`](https://github.com/Shopify/shopify-app-js/tree/main/packages/apps/shopify-api); the docs include current OAuth/API guidance. This is directly relevant to `inventory/connectors/shopify.js`, `inventory/http.js`, `inventory/ingress.js`, `inventory/connections.js` and `inventory/connection-setup.js`.

Local Shopify ingress source already verifies HMAC over raw bytes in `inventory/connectors/shopify.js`, requires delivery IDs, hashes payloads, rejects changed-body replay and writes the receipt and order effect in one PostgreSQL transaction in `inventory/ingress.js`. The provider package is therefore a targeted reference for current API/OAuth semantics and version migration, not proof that local HMAC/idempotency must be replaced. The archived prior repository is not a recommended dependency.

Vendure maintenance evidence is more specific than a generic “active” label: current [v3.7.4 release notes](https://github.com/vendurehq/vendure/releases) describe a corrected last-unit oversell caused by an unlocked read-modify-write and a saleable-stock check separated from allocation; the correction locks StockLevel rows, under-allocates losing orders and emits a shortfall event. The same release reports an API-key privilege-escalation fix. This shows both a useful acceptance test and why an active upstream project is not proof every earlier version was safe. This is a useful source for the test cases to require locally. It does not remove Vendure's framework and GPL compatibility costs.
