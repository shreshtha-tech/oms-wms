# Independent PostgreSQL inbox/outbox: storage → polling → effect → completion

Pinned Zehelein/pg-transactional-outbox revision `5556d4532961907ac88d1fdd4c6c02ca9c6bc35d`; MIT license read. UP-019. This is a library API workflow; HTTP authentication and marketplace contracts are NOT APPLICABLE to the library itself. Source and test assertions read; downloaded code and generated setup SQL NOT EXECUTED.

1. [lib/src/message/initialize-message-storage.ts](https://github.com/Zehelein/pg-transactional-outbox/blob/5556d4532961907ac88d1fdd4c6c02ca9c6bc35d/lib/src/message/initialize-message-storage.ts) accepts message and caller-provided database client. It inserts identity, aggregate/type, segment, payload and metadata using parameterized values. Duplicate identity is ON CONFLICT DO NOTHING with warning; **it does not compare a canonical payload digest**. The caller must provide the transaction connecting business change and message insertion. Client parameter alone cannot prove every application does so.
2. [lib/src/setup/database-setup.ts](https://github.com/Zehelein/pg-transactional-outbox/blob/5556d4532961907ac88d1fdd4c6c02ca9c6bc35d/lib/src/setup/database-setup.ts) defines storage with processed/abandoned/locked timestamps and attempt counts. Its generated next-message function takes the oldest outstanding item per segment, skips unexpired lease and NOWAIT lock/serialization failures, fills spare capacity with parallel messages, then updates lease and started attempts. The oldest leased item can block later same-segment work deliberately; fairness and global throughput are policy choices. This is not SKIP LOCKED SQL. Setup also contains destructive table replacement: NEVER run it against this checkout's database.
3. [lib/src/polling/next-messages.ts](https://github.com/Zehelein/pg-transactional-outbox/blob/5556d4532961907ac88d1fdd4c6c02ca9c6bc35d/lib/src/polling/next-messages.ts) calls the configured SQL function in a REPEATABLE READ transaction and maps returned data. `polling-message-listener.ts` creates the handler and error-handler, fetches a batch, invokes handlers with timeout observers and passes failures to the error handler. Per-message batch processing can run concurrently; SQL segment selection supplies ordering discipline.
4. [lib/src/handler/create-message-handler.ts](https://github.com/Zehelein/pg-transactional-outbox/blob/5556d4532961907ac88d1fdd4c6c02ca9c6bc35d/lib/src/handler/create-message-handler.ts) checks handler selection and poisonous-message policy. `message/initiate-message-processing.ts` reacquires NOWAIT row lock on the processing transaction and reloads current processed/abandoned state before effects. Already processed/abandoned/missing returns without calling the effect handler. No-handler policy instead completes the message: do not adopt for unknown inventory command types.
5. `handler.handle(message, client)` and `markMessageCompleted` share the same transaction/client, latter sets processed_at and increments finished attempts. `common/utils.ts:executeTransaction` begins, awaits callback, commits and releases; errors attempt rollback and release while preserving original error. **Only database effects performed on this client share atomicity. An HTTP shipment request cannot be rolled back by this function.**
6. Timeout observer sets timedOut, attempts rollback and closes/releases the client. transactionFinished is checked before touching the client and again after awaited rollback, preventing a late observer from releasing a successfully returned client. Mark-complete is skipped after timeout. This is a useful client-lifetime invariant, not a guarantee that an external effect ceased.
7. `handler/create-error-handler.ts` uses retry/abandon policy and best-effort metadata updates. Serialization/deadlock update failures retry up to three times with short linear delay. `strategies/message-retry-strategy.ts` permits serialization/deadlock work up to the larger of configured attempts and 100; ordinary failures use finished-attempt cap. This potentially aggressive database-failure policy must not become generic retries of remotely uncertain mutation.

## Tests and boundaries

[lib/src/handler/create-message-handler.spec.ts](https://github.com/Zehelein/pg-transactional-outbox/blob/5556d4532961907ac88d1fdd4c6c02ca9c6bc35d/lib/src/handler/create-message-handler.spec.ts) explicitly checks: no handler marks complete; timeout after completion adds no rollback/release; timeout queued behind COMMIT does not double-release; handler finishing after timeout cannot mark processed and preserves original closed-client error. These tests use pool-like controlled clients and deferred promises; they are NOT a PostgreSQL network-loss or real crash campaign. `polling/next-messages.spec.ts` checks mapping and empty results, not the SQL locking function itself. Additional test files exist but are not counted as inspected assertions here. All upstream execution NOT RUN.

## Comparison and decision

Local LOC-002/003/019 reject conflicting canonical message identity and validate command semantics; keep those stronger checks rather than silently ignoring any repeated UUID. Local claim ownership and uncertain commit/projection state remain necessary. Borrow late-timeout/client-lifetime test ideas under R-03; keep remote publication UNKNOWN/READBACK_PENDING held under LOC-007. For the confirmed LOC-016 deadlock, prefer common internal lock order and whole local transaction retry with stable identity; a library's high retry cap is not a substitute for fixing inverted lock order. No dependency introduction is warranted.
