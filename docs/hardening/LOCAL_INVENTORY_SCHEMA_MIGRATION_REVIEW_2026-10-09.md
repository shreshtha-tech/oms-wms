# Local inventory schema migration review — 2026-10-09

The configured inventory PostgreSQL target was verified as loopback. Its current read-only schema diagnosis found `ci_event_receipt` and `ci_domain_outbox` absent, all 17 outbox publication columns absent, and both channel-stock readback columns absent. The local app's public readiness returned `SCHEMA_UNAVAILABLE`, while older overview queries still returned catalog rows. This is a local configured-database finding; it is not hosted or production evidence.

`scripts/rehearse-local-schema-migrations.mjs` streamed **schema only** from that configured database into a fresh owned PostgreSQL process. It asserted zero SKU and outbox rows in the clone, ran the current `migrateInventory` sequence through migration 029, and executed the mounted readiness SQL. Result: PASS, readiness true. The script removed only its owned process and temporary data. No configured table or row was changed, and no business data was copied. This proves compatibility with the current schema shape, not with current data or production load.

`scripts/preflight-local-inventory-migration.mjs` inspected counts under `BEGIN READ ONLY` with a 5-second statement deadline. Result: PASS. Migration 021 would copy zero historical alert rows; no existing unified order has a work status outside the new allowed set. The original migration 022 would have set `providerAuthoritative=true` on **3 existing channel accounts**: one Flipkart and two Shopify. The dispatch gate consumes that flag only for WooCommerce and Amazon. Migration 022 was therefore narrowed to those two platforms; the current preflight shows **zero** eligible local accounts. Migration 023 found zero duplicate `(tenant_id,id)` inventory events. These counts do not verify account ownership, provider capability, tenant policy, indexes, transaction lock duration, or rollback under production load.

The configured loopback database measured 18,052,799 bytes. A data-bearing run of `rehearse-local-schema-migrations.mjs --with-data` made a private temporary custom-format backup, restored it into a fresh owned loopback PostgreSQL process, and deleted both the archive and fixture after verification. The clone matched source row counts for 3,243 SKUs, zero outbox tasks, and three channel accounts. Migrations 001–029 completed and readiness returned true. Before/after fingerprints of the clone's inventory events, balances, reservations and unified orders matched exactly; SKU and account row counts were preserved. None of the three unrelated accounts received a Stage 1 authority grant. The fixture also simulated a historical automatic grant on one unrelated account and an explicit operator grant on another: migration 029 revoked only the old automatic grant, wrote a revisioned audit row, and preserved the operator decision. Result: PASS. This is a real data-bearing local restore/migration rehearsal, but its temporary archive is not a retained recovery backup and the source may change after the snapshot.

The 022 cutover is an intentional Stage 1 policy recorded in `docs/architecture/PHASE_B_EVIDENCE_2026-10-07.md`: existing Woo/Amazon full-shipment deduction compatibility is preserved through an audited one-time provider-authoritative flag, while new accounts default off. Migration 029 corrects only previously automatic non-Woo/Amazon grants when the current revision still matches the original migration audit. The fresh two-store `verify-phase-b-dispatch.mjs` suite PASS confirmed an existing WooCommerce account retains dispatch authority, a preexisting Shopify account receives none, a new account defaults off, and Amazon partial shipments remain review-only. The migration also adds constraints and indexes, including concurrent receipt-claim indexes; their build time and lock interaction have not been measured on the populated target. A retained configured recovery backup is not available in this review.

Runtime authority continuation: the `POST /api/inventory-sync/connections/:id/provider-authority` endpoint now requires the explicit `central_inventory.provider_authority.manage` permission and rejects enable requests for platforms other than WooCommerce/Amazon. Its tenant-scoped row lock and expected revision remain. The same fresh two-store suite PASS verified 403 without permission, 400 for a permitted user enabling Shopify, 404 for a foreign-tenant account ID, 409 for a stale revision, and successful revisioned/audited WooCommerce/Amazon changes. None of these denied requests changed the target account revision. Configured operator permissions and hosted enforcement remain unverified; the new permission is deny-by-default and must be granted deliberately.

The fresh isolated session-recovery suite also PASS after the permission addition: configured account parsing accepts the explicit new grant, the stock-count-only operator receives 403 for the authority guard, the granted fixture passes, and login, hashed session persistence, rotation, expiry, logout and protected-route checks remain green. These are synthetic account fixtures, not a review of actual operator grants.

**Decision:** configured migration NOT RUN. The source schema is demonstrably stale, and a data-bearing clone upgrades without changing ledger or order rows. A retained, verified backup with recovery location, account-policy review, live lock/traffic window and post-migration checks remain required before changing the configured database. The MongoDB TLS handshake problem is independent and will not be fixed by PostgreSQL migrations.
