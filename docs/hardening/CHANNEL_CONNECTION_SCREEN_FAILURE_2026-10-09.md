## Confirmed UI cause and repair

`src/lib/api.ts` recorded every failed GET as a page-level failure. `src/eretail/Shell.tsx` hid its children when any page-level failure existed. `src/pages/CentralInventory.tsx` also handled publication-status errors locally, but the shell hid the entire channel connections view before that local message could help. This turned a publication-monitoring failure into an apparent connection-screen outage.

The publication-status request and connection-panel reads now use `apiGetLocal`, so their errors remain in those panels. A failed publication read clears its prior rows and displays the error; it cannot hide the connection controls. Critical overview reads retain the page-level boundary. The regression verifies that a simulated publication HTTP 503 does not register a page failure while a critical overview HTTP 503 still does. No provider call, credential, database record or stock publication was changed.

A rendered Chrome fixture then exposed a separate loading race. The initial overview effect depended on `data.generatedAt`; on a successful response, `setData` changed that dependency and cleaned up the effect before its `finally` cleared `loading`. The view could remain at “Loading inventory…” indefinitely. The effect now depends on the selected section and stable refresh function, so a successful overview completes the loading state. The rendered fixture PASS confirms the channel heading, Refresh connections control and publication panel remain visible under a mocked publication HTTP 503. The summary and programme widgets also use their existing local error states instead of hiding the workspace.
